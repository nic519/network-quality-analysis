# Clash Speedtest 导航拆分设计

## 目标

将当前桌面界面重构为更清晰的分区视图，把测试执行、结果分析、工具诊断拆开，同时修正当前 `clash-speedtest` 状态语义不准确的问题，避免把 GitHub 更新检查失败误显示为软件本身异常。

## 本次范围

- 将当前单页仪表盘拆成 3 个顶层视图：
  - `执行测试`
  - `结果分析`
  - `依赖与诊断`
- 保留现有延迟测试、历史记录、CSV 导出能力。
- 将 `clash-speedtest` 的详细状态从首页主区域移出，改为单独诊断页展示。
- 在全局头部保留一个轻量级状态摘要，让用户随时知道当前是否可直接发起测试。
- 调整 `clash-speedtest` 的状态语义和文案，使“更新检查失败”和“真实不可用”明确区分。
- 将当前过大的 React 入口文件拆分为更小、更聚焦的视图与面板组件。

## 不在本次范围

- 多窗口模式。
- 数据库结构调整或新增持久化模型。
- 自动后台重试下载或自动轮询更新。
- 跨平台打包方案变更。
- 在现有图表之外新增更复杂的分析图表。

## 要解决的用户问题

### 1. 当前界面把不同任务堆在一起

现在用户无论是想“发起一次测试”、还是“查看历史结果”、还是“排查 `clash-speedtest` 当前状态”，都需要在同一长页面里来回扫视，认知负担较高，也会让应用显得杂乱。

### 2. 当前 `clash-speedtest` 状态文案会误导用户

当本地还没有下载二进制，同时 GitHub 最新版本检查失败时，界面会显示 `状态异常`。这会让用户误以为程序本身坏了，但真实原因可能只是 GitHub API 限流、网络超时，或者临时无法确认最新版本。

### 3. 当前文件结构不利于继续演进

`src/mainview/src/App.tsx` 目前同时承担了应用状态管理、页面布局、状态展示、测试配置、图表展示、筛选逻辑、指标卡片和进度日志等职责。后续继续改 UI，风险和维护成本都会越来越高。

## 信息架构

### 顶层导航

应用应提供一个固定的顶层导航，包含 3 个标签页：

- `执行测试`
  - 用途：配置并发起一次新的测试。
  - 主要内容：配置路径输入、最近使用记录、地区选择、启动按钮、进度日志、运行时错误提示。

- `结果分析`
  - 用途：查看当前和历史测试结果。
  - 主要内容：指标概览、批次与日期筛选、节点搜索、站点切换、延迟排行图、不可用节点提示、CSV 导出。

- `依赖与诊断`
  - 用途：查看打包工具 `clash-speedtest` 的状态，并理解当前失败原因。
  - 主要内容：本地安装状态、路径、来源、当前版本、远端最新版本、最近检查时间、更新检查结果、故障说明和建议。

### 全局快速状态

即使用户不在诊断页，也应在头部保留一个简洁的工具状态摘要，用来回答“现在能不能直接开始测试”。这个摘要只负责表达：

- 已可运行
- 正在下载
- 正在检查更新
- 尚未下载，首次运行会自动准备
- 建议查看诊断

更详细的解释和故障细节，统一放在 `依赖与诊断` 页中。

## 状态模型调整

当前 `ClashSpeedtestState.status` 的粒度偏粗，因为 `error` 混合了“真实准备失败”和“只是远端更新检查失败”两种完全不同的语义。新的设计应做到：

- `missing`
  - 本地尚未发现可用二进制。
- `ready`
  - 本地存在可用二进制，当前可直接运行。
- `downloading`
  - 正在下载或安装二进制。
- `checking-update`
  - 正在查询远端最新版本。
- `error`
  - 出现了真正影响测试执行的准备失败或启动失败。

同时，宿主侧需要把“更新检查结果”单独表达出来，而不是继续混进 `status`。建议最小新增字段：

- `updateCheckStatus: "idle" | "ok" | "failed"`
- `updateCheckMessage: string | null`

这样 `status` 只描述“本地工具当前能否用”，而更新检查相关信息则作为诊断补充字段使用。

## 状态语义约定

### 不应再显示为“状态异常”的情况

- GitHub API 被限流。
- 查询最新版本时网络超时。
- 本地尚未下载，但远端最新版本暂时无法确认。
- 本地已有可用版本，但远端最新版本查询失败。

这些情况应该改成更准确的表达，例如：

- `未完成更新检查，可继续首次下载`
- `更新检查失败，但本地版本可继续使用`
- `GitHub 检查失败：403 rate limited`

### 仍应视为真实错误的情况

- 首次下载失败。
- 压缩包解压失败。
- 已解析到二进制路径，但可执行文件无法运行。
- 启动测试时因为缺少或损坏的二进制而失败。

这些情况仍然可以使用 `error`，因为它们确实影响用户发起测试。

## UI 布局设计

### 页头

- 保留产品标题与简短说明。
- 在标题附近加入顶层导航标签。
- 当当前页是 `执行测试` 时，主要操作按钮应保持靠近头部，形成明显的启动入口。
- 当当前页切换到其他标签时，头部区域可改为显示轻量状态摘要，或显示与当前页相关的次级操作。

### `执行测试` 页

- 以配置路径输入区域为主要起点。
- 地区选择紧跟配置输入区域，便于完成一次完整配置。
- `开始测试` 按钮应保持视觉主导地位。
- 进度日志只在这里展示，不再与结果分析混在一起。
- 如果工具状态需要关注，应提供一条简短提示，并附带跳转到 `依赖与诊断` 页的入口。

### `结果分析` 页

- 先展示概览指标。
- 批次、日期筛选和节点搜索集中在一起。
- 站点切换紧贴图表区域。
- CSV 导出属于结果操作，因此放在这个页面，而不是放在测试配置页。

### `依赖与诊断` 页

- 把 `clash-speedtest` 当作一个可检查的运行依赖来展示，而不是首页里的一条警告状态。
- 页面中需要呈现：
  - 当前内置版本
  - 已知远端最新版本
  - 更新检查状态
  - 本地安装路径
  - 安装来源（`cache` 或 `environment`）
  - 最近检查时间
  - 当前建议或诊断结论
- 当“本地未下载 + 远端检查失败”同时出现时，要明确告诉用户：
  - 当前失败影响的是“是否能确认最新版本”
  - 不等于应用已经损坏
  - 首次运行的自动下载仍可能在后续网络恢复后成功

## 组件拆分方案

当前 React 文件需要按职责拆开。文件名可以结合项目现有风格调整，但职责边界应明确为：

- `App`
  - 管理顶层状态、当前标签页、RPC 生命周期。
- `TopNavigation`
  - 渲染三段式导航和全局快速状态。
- `RunSetupView`
  - 渲染配置路径、地区选择、启动操作、进度日志。
- `AnalysisView`
  - 渲染概览指标、筛选器、图表、不可用结果提示和导出按钮。
- `DiagnosticsView`
  - 渲染完整的 `clash-speedtest` 依赖状态和诊断说明。
- `ClashSpeedtestQuickStatus`
  - 头部使用的紧凑型状态摘要。
- `ClashSpeedtestDiagnosticsPanel`
  - 只在诊断页使用的详细状态面板。

像状态标签、颜色映射、诊断文案组装这类展示逻辑，也应从 `App.tsx` 移走，放到更聚焦的组件文件或辅助函数里，保证后续更容易测试和维护。

## Bun 宿主侧行为

宿主侧继续保留现有测试流程，但对外发布的状态需要更精确：

- 应用初次加载时：
  - 先检查本地安装状态
  - 再尝试查询远端最新版本
  - 最终同时发布“本地可用状态”和“更新检查结果”

- 首次运行测试时：
  - 如果本地没有二进制，则发布 `downloading`
  - 下载成功后发布 `ready`
  - 下载或启动失败时发布 `error`

- 每次测试完成后：
  - 使用新的状态模型重新刷新一次工具状态

关键约束是：不能再因为远端更新检查失败，就把一个本地其实可用的状态覆盖成通用 `error`。

## 文案方向

所有状态文案都应更具体、可行动，避免笼统告警。建议表达顺序为：

- 先说当前状态
- 再说影响
- 最后在已知时补充原因

示例：

- `未检测到本地 clash-speedtest，首次运行时会自动下载。`
- `更新检查失败，但本地版本仍可继续使用。`
- `GitHub 返回 403，当前无法确认最新版本。`
- `下载失败，暂时无法开始测试。`

## 测试要求

### 宿主侧测试

- 验证“本地缺失 + 更新检查失败”时，不应直接变成阻塞性的通用错误状态，除非真实下载或启动也失败。
- 验证“本地存在 + 更新检查失败”时，仍应保持可用状态，只是附带降级的更新信息。
- 验证真实下载失败时，仍然正确发布 `error`。

### UI 测试

- 验证三段导航切换后内容正确变化。
- 验证进度日志只出现在 `执行测试` 页。
- 验证导出操作只出现在 `结果分析` 页。
- 验证诊断页能展示完整依赖信息，并在“更新检查失败”时使用非误导性的说明文案。

## 验收标准

- 用户可以在 `执行测试`、`结果分析`、`依赖与诊断` 三个视图之间清晰切换。
- 默认落地页为 `执行测试`。
- `App.tsx` 不再内联承载所有主要页面内容。
- `clash-speedtest` 的更新检查失败，不再被统一渲染成笼统的“状态异常”，除非工具真的不可用于测试。
- 诊断页能够明确区分以下几类情况：
  - 本地未下载
  - 远端更新检查失败
  - 正在下载
  - 真实启动或准备失败
- 现有测试执行、结果筛选、图表展示和 CSV 导出能力保持可用。
